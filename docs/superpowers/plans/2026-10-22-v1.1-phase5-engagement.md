# v1.1 Phase 5 — Achievements & engagement

**Spec:** `.omc/specs/deep-interview-v1.1-phase5-engagement.md` (deep interview, 19% ambiguity) and
`docs/superpowers/specs/2026-10-16-v1.1-roadmap.md` → Phase 5.
Status: pending approval (consensus final).

**Goal:** badges get a rarity tier and an optional Discord role; events record
attendance by QR (player scans the event, or staff scan the player); events
send reminders and offer a calendar file; players get an in-site bell. Website
side only: schema, RPCs, admin/player UI, a bot contract doc and local mocks.
The Discord bot is updated separately against the contract.

## Requirements summary

Five components, one plan (spec Topology):

| # | Component | Spec AC |
|---|---|---|
| A | Rarity tier + player-picked showcase | 1–3 |
| B | Achievement → Discord role queue | 4–6 |
| C | Event check-in / attendance | 7–12 |
| D | Event reminders + `.ics` | 13–15 |
| E | Notification bell | 16–19 |

Roadmap change carried from the interview: check-in records **attendance only**
(no auto-award); staff award attendees in one click.

## Decisions

- **Data pattern unchanged.** Every new table: RLS on, `revoke all` from
  anon/authenticated, no policies; reads and writes through `security definer`
  RPCs with `set search_path = ''` and an explicit grant. Staff writes check
  `public.staff_can('community')` (`20261019000001_staff_roles.sql:23`, which
  already covers `event_staff`) and call `log_account_change`. Bot RPCs are
  `service_role` only and pull-based, like `announcements_discord_queue()`
  (`20261009000001_announcements.sql:166`). Each migration adds its new
  anon/authenticated grants to the allowlist in
  `supabase/tests/default_function_privileges.test.sql`; that test does not
  cover `service_role`, so each migration's own test asserts
  `has_function_privilege('service_role', …)` for its bot RPCs (true) and for
  anon/authenticated (false).
- **service_role table access.** Tables holding secrets or codes
  (`event_checkin_secrets`, `player_checkin_codes`) also `revoke all … from
  service_role`, as `announcements` does (`20261009000001:38`); the bot never
  needs them. Other new tables keep the default (service_role can read), which
  is accepted: it already holds the secret key.
- **Signatures stay put.** `admin_upsert_achievement` / `admin_upsert_event`
  were rewritten in place by the staff-roles DO block
  (`20261019000001:62-112`); new fields get their own setter RPC called right
  after the upsert, the same way `admin_set_event_category` and
  `admin_set_event_banner` are (`src/app/admin/commu/events/[id]/actions.ts:86-88`).
- **Tier:** `achievements.tier` ∈ `common | rare | epic | legendary`, default
  `common` (existing rows migrate to Common). Tier sets the card frame colour and
  is always also in text (visible chip + accessible name), never colour-only.
  Colours live as `--tier-*` tokens in `src/app/globals.css` (light + dark).
- **Showcase:** up to **3** picks per player (open default, Q2). Empty pick
  falls back to highest tier, then newest `last_on`. Fallback is computed in TS
  from `achievement_groups` (which gains `tier` and `showcase_position`), so
  `player_card` (`20261007000001_social.sql:184`) is not rewritten.
- **Discord roles: owner/admin-curated allowlist** (security, A1). A badge can
  only map to a role in `discord_assignable_roles`, which only
  `staff_can('admin')` (owner/admin) edits on `/admin/settings`. Community
  staff then pick from that list on the achievement form (a select, not free
  text), which keeps the spec's "role mapping is a community-staff edit on the
  achievement form" without letting `event_staff` map a badge to a moderator
  role and self-award it via award-attendees. Chosen over "mapping is
  admin-only" because event staff create most badges. The DB cannot know the
  bot's own role IDs, so the contract also requires the bot to refuse any role
  it manages itself (verified, faculty/unit/Graduate from verified-role-sync)
  and relies on Discord hierarchy (a bot can only assign roles below its top
  role).
- **Discord role queue = derived state + status ledger** (see RALPLAN-DR).
  Desired pairs = awards × **published** achievements with a role × the
  player's Discord identity, **excluding banned players** (`is_banned`,
  `20261012000001_bans.sql:44`): a ban removes badge roles and lifting it
  restores them; drafting a mapped badge removes its role. The ledger
  `discord_role_state` records per pair `status applied|failed`, `attempts`,
  `retry_after`, `last_error`. Queue = desired − applied (`add`, unless failed
  and not yet due) ∪ applied − desired (`remove`, unless a failed remove is not
  yet due). A failed **remove** keeps `status = 'applied'` (the role is still on
  the member) and only sets `attempts`/`retry_after`/`last_error`, so it is never
  lost. Award/revoke RPCs are not touched.
- **Check-in token = HMAC time window** (see RALPLAN-DR). Per-event secret in
  `event_checkin_secrets`, created lazily by `admin_checkin_token`
  (`insert … on conflict do nothing`), rotatable by `admin_rotate_checkin_secret`.
  Token = `<window>.<mac>`, window = `floor(epoch / 30)`, mac = base64url of the
  first 16 bytes of `extensions.hmac(event_id || ':' || window, secret, 'sha256')`.
  Current and previous window accepted (max life 60 s).
- **Sign-in proof (C1).** The QR points at a route handler
  `/events/[id]/check-in/start?t=…`. It verifies the token through
  `checkin_proof(event, token)` (granted to anon and authenticated), which
  returns a **proof** `p.<expires_epoch>.<mac>` valid 5 min, signed with the same
  per-event secret over a domain-separated message
  `'proof:' || event_id || ':' || expires` (tokens sign `'token:' || event_id || ':' || window`),
  so a token MAC can never pass as a proof or the reverse. `checkin_proof`
  accepts only the `<window>.<mac>` token form, so a proof cannot mint a fresh proof. The handler stores it in an httpOnly, SameSite=Lax cookie
  scoped to `/events/<id>/check-in`, `Max-Age=300`, then redirects to the page
  (signed in) or `/register` (signed out). It binds the proof to the event,
  not the user, because the user may not exist yet. `check_in` accepts a token or a proof. A
  route handler is needed because Server Components cannot set cookies
  (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md:81`).
- **Return after sign-in.** `src/app/auth/callback/route.ts:20-22` deliberately
  never lets callback parameters choose the redirect, so no `next` query param.
  Instead the start handler sets a second cookie `cc_next` holding the path
  (`Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=600`).
  `src/lib/safe-next.ts` `safeNext()` accepts only `^/events/<uuid>/check-in$`.
  `/welcome` is a Server Component and cannot delete cookies (`cookies.md:81`),
  so after its profile check (`src/app/welcome/page.tsx:46`) it only reads
  `cc_next` and, when `safeNext()` accepts it, redirects to a small route handler
  `src/app/check-in/continue/route.ts`, which clears the cookie and redirects to
  `safeNext(value)` (or `/dashboard`). The `checkIn` action also clears it.
  Sign-in paths that skip `/welcome` (`/verify` for unverified,
  `/settings?error=…` from `src/lib/reconcile-identities.ts:76-77`) leave the
  cookie to expire; the player rescans → "Scan the code again". Proof expired
  by then → same message.
- **Check-in window:** one rule, built on `event_is_ended`'s
  `coalesce(ends_at, starts_at)` (`20261006000002_event_interest.sql:45-47`):
  open from `starts_at − 15 min` to `coalesce(ends_at, starts_at) + 15 min`.
  One helper `checkin_open(events)` used by token, proof, self scan and staff
  scan. The event form hint says "Set an end time to keep check-in open".
- **Personal QR:** encodes the bare code text `CC-XXXXXXXXXX` (10 chars from
  `A-Z2-9`, no URL, so a phone camera opens nothing). Stored in
  `player_checkin_codes`, created on first read by `my_checkin_code()`.
  Staff scan returns the player's name + avatar so staff can eyeball a shared
  screenshot.
- **QR rendering:** one dependency `qrcode@1.5.4` (+ devDependency
  `@types/qrcode`), used **server-side only**: server action `nextToken` returns
  `{ svg, expiresAt }`; `checkin-qr.tsx` renders
  `<img src="data:image/svg+xml;utf8,…">` (CSP `img-src` allows `data:`,
  `src/proxy.ts:32`) and never imports `qrcode`. Refresh is scheduled from
  `expiresAt`. Hand-writing an encoder is out of proportion. **Scanning** uses
  native `BarcodeDetector` with a manual code field always visible; no scanner library.
- **Camera:** `next.config.ts:50` sends `Permissions-Policy: camera=(), microphone=(), geolocation=()`
  (verified: line 50). Add a later header rule for
  `/admin/commu/events/:id/check-in` restating the full value
  `camera=(self), microphone=(), geolocation=()`, because the whole key is replaced.
  The last matching header key wins
  (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/headers.md:47`),
  so the camera stays off everywhere else.
- **Event history** comes from attendance (newest first) with badges earned at
  that event; `eventHistory()` (`src/components/achievement-grid.tsx:31`) and its
  test cases are removed. Existing event-linked awards are **backfilled** into
  attendance (`method 'backfill'`, published events only), so the `/dashboard`
  "Events" stat (`src/app/dashboard/page.tsx:155`) keeps its value.
- **Reminders:** offsets chosen per event from presets (1 week, 1 day, 3 h,
  1 h, 15 min). Due = `starts_at − offset`. Per event only the **latest due**
  unsent offset (smallest offset whose due time has passed) is offered; older
  unsent ones are marked `skipped_at`. Offsets already past when staff save
  them are skipped at once. A reminder whose event has started is never
  offered. Moving `starts_at` re-arms offsets whose new due time is ahead.
- **Reminder delivery (open default, Q1):** bot posts in the announcements
  channel and pings players who marked interest and have a linked Discord. The
  queue returns those Discord IDs; DM would use the same rows.
- **Reminder bell is independent of the bot** (adopted in rev 2): a pg_cron job
  every 5 min, `event_reminders_notify()`, applies the same "latest due" rule,
  sets `notified_at` and inserts bell rows. Discord (`sent_at`) and bell
  (`notified_at`) are tracked separately. A re-armed reminder notifies again,
  because the time changed.
- **`.ics`:** route handler `src/app/events/[id]/calendar.ics/route.ts`
  (`params` is a Promise, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md:82`).
  Times in UTC (`…Z`), no VTIMEZONE; DTEND = `ends_at` or `starts_at + 2 h`.
  Reads `get_event` (published only), so a draft is 404. Filename = slug of the
  name, or the event id when the (Thai) name slugifies to empty.
- **Notifications:** created in the database only, never by app code. Kinds: `award`, `appeal`,
  `report`, `banner`, `reminder`. Award and banner use **statement-level**
  `AFTER INSERT … REFERENCING NEW TABLE` triggers, set-based over the whole
  `admin_award` batch. Appeal and report are row-level `AFTER UPDATE OF status`
  (one row per RPC call; transition tables can't be combined with a column
  list). Reminder is the cron job above. Header reads the unread count on full
  page load (`src/components/site-header.tsx:19-20`); no Realtime. Opening
  loads the last 20 and marks all unread read. Daily pg_cron deletes rows
  older than 90 days (pg_cron already used, `20261017000002_stats_daily.sql:45-46`).
- **UI baseline for every UI task:** Thai font stack and Thai-safe copy (no
  truncation of Thai names), loading/empty/error/success states, 375 px without
  horizontal scroll, keyboard reachable, no motion under `prefers-reduced-motion`.

### B. Discord roles

#### 4. Migration `20261026000002_achievement_discord_roles.sql` + `achievement_discord_roles.test.sql`
- `discord_role_state (discord_id, role_id, status text check (status in ('applied','failed')),
  attempts int default 0, retry_after timestamptz, last_error text, updated_at,
  pk (discord_id, role_id))`, RLS on, no grants to anon/authenticated.
- Internal `discord_role_desired()` (ungranted): distinct
  `(i.provider_id, a.discord_role_id)` from `achievement_awards w` ⨝
  `achievements a` (published, role not null) ⨝ `auth.identities i`
  (`provider = 'discord'`, as `verified_members`, `20261005000001:24-27`),
  where `not public.is_banned(w.user_id)`.
- `discord_role_queue()` → `(discord_id, role_id, op 'add'|'remove')`,
  `limit 100`, `service_role` only. `add`: desired and no ledger row, or
  `failed` with `retry_after <= now()`. `remove`: `applied`, not desired, and
  `retry_after is null or retry_after <= now()`. A `failed` row (a failed
  **add**) that is no longer desired is deleted by the next write-back; an
  `applied` row is only ever deleted by an `ok` remove.
- `discord_role_queue_done(p_items jsonb)` → int, `service_role` only; item
  `{discord_id, role_id, op, ok, error?}`. `ok` add → `applied`; `ok` remove →
  row deleted; not `ok` add → `status 'failed'`; not `ok` remove → status stays
  `applied`; both set `attempts + 1`,
  `retry_after = now() + least(2^attempts minutes, 24 h)`, `last_error`. An `ok`
  write-back resets `attempts`/`retry_after`. Unknown
  op → `INVALID`. Facts only; the next read re-derives, so a race self-corrects.
- Test: mapped award → one `add`; ok write-back clears it; failed write-back
  hides it until `retry_after`, then it returns; failed **remove** write-back
  keeps the row `applied`, hides the `remove` until `retry_after`, then
  re-queues it; second award of same badge →
  nothing; revoking one of two awards → nothing; revoking the last → `remove`;
  drafting the badge → `remove`; banning → `remove`, lifting → `add`; unmapped /
  unlinked player → never listed; changing role → `remove` old + `add` new;
  `has_function_privilege` true for service_role, false for anon/authenticated.

### C. Check-in and attendance

#### 5. Migration `20261027000001_event_attendance.sql` + `event_attendance.test.sql`
- Opens with the pgcrypto schema assert (task 0).
- Tables, RLS on, `revoke all` from anon/authenticated:
  `event_attendance (event_id, user_id, method text check (method in ('self','staff','backfill')),
  recorded_by, created_at, pk (event_id, user_id))`;
  `event_checkin_secrets (event_id pk, secret bytea not null default extensions.gen_random_bytes(32), rotated_at)`
  and `player_checkin_codes (user_id pk, code text unique check (code ~ '^CC-[A-Z2-9]{10}$'))`,
  both also `revoke all … from service_role`. `account_change_log_entity_check`
  re-created with `event_attendance` added (full list from
  `20261025000001_site_content.sql:14-17`).
- **Backfill:** `insert into event_attendance (event_id, user_id, method)
  select distinct w.event_id, w.user_id, 'backfill' from achievement_awards w
  join events e on e.id = w.event_id and e.status = 'published' on conflict do nothing`.
- Helpers (ungranted): `checkin_open(public.events)`,
  `checkin_mac(event_id, text)`, `checkin_verify(event_id, text) → boolean`.
  Any parse/cast failure inside verify is caught and returns false, so a
  malformed token gives `TOKEN_EXPIRED`, never `22P02`. No secret row → false.
  Compare: `extensions.digest(given) = extensions.digest(expected)` (double hash),
  so timing reveals nothing about the mac. A plain compare would be
  noise-dominated over PostgREST anyway, and a mac lives 60 s.
- `admin_checkin_token(p_event_id)` → `(token, expires_at)`; community staff;
  inserts the secret `on conflict do nothing` then reads it; `NOT_FOUND` for
  draft/missing, `CHECKIN_CLOSED` outside the window.
- `admin_rotate_checkin_secret(p_event_id)`: new secret, logged; old tokens and
  proofs stop working at once.
- `checkin_proof(p_event_id, p_token)` → text or null (anon, authenticated);
  token form only (`^[0-9]+\.[A-Za-z0-9_-]{22}$`), so a proof passed in → null.
- `check_in(p_event_id uuid, p_token text)` → `'recorded' | 'already'`
  (authenticated), accepts token or proof; `NOT_FOUND`, `CHECKIN_CLOSED`,
  `TOKEN_EXPIRED`, `BANNED`. `on conflict do nothing`.
- `my_checkin_code()` → text: `insert … on conflict (user_id) do nothing` with a
  random code, retry up to 5 times on `unique_violation` of `code`, then select.
- `admin_check_in_player(p_event_id, p_code)` →
  `(status, user_id, display_name, avatar_url)`; `UNKNOWN_CODE`,
  `CHECKIN_CLOSED`, `BANNED`; logs `event_attendance` / `checked_in`.
- `admin_list_attendance(p_event_id)`, `admin_remove_attendance(p_event_id, p_user_id)` (logged with old method).
- `admin_award_attendees(p_event_id, p_achievement_id)` → int: takes
  `pg_advisory_xact_lock(hashtextextended(p_event_id::text || p_achievement_id::text, 0))`
  (no unique key on `achievement_awards`), then passes attendees not holding
  the badge to `admin_award(p_achievement_id, p_event_id, null, …)`
  (`20261006000001:244`, one log row per recipient), plus one `events` /
  `award_attendees` row with the count.
- Player reads: `my_event_history()`, `get_player_event_history(p_user_id)` →
  jsonb `[{event_id, name, starts_at, badges}]`, published events/badges only,
  newest first; the latter `NOT_FOUND` when blocked either way, `[]` unless
  `can_view(viewer, target, 'achievements')`.
- Test:
  - Tokens: windows w and w−1 are accepted; w−2, a forged mac, a malformed string (`'x'`, `'1.'`) and a missing secret all give `TOKEN_EXPIRED`.
  - Window: a scan before or after the grace gives `CHECKIN_CLOSED`.
  - Proof: accepted until it expires, refused after rotation; a proof passed to
    `checkin_proof` → null (no self-renewal); a token MAC presented as a proof is refused.
  - Repeat: a second scan returns `'already'` and there is still one row.
  - Banned: refused on both paths.
  - Staff code: an unknown code is refused.
  - `my_checkin_code`: stable across calls.
  - Award attendees:
    - skips holders and returns the count;
    - writes N recipient log rows plus 1 event log row;
    - called twice, the second call returns 0 with no duplicate awards;
    - a player and anon get `FORBIDDEN`, event_staff is allowed.
  - Backfill: covers published events only.
  - History: ordered newest first, drafts filtered out, blocked gives `NOT_FOUND`.
  - Privileges: service_role has no access to the secrets or codes tables.

## RALPLAN-DR summary (mode: SHORT)

**Principles**
1. Database is the gate: every rule (role, window, ownership, who may map a role) lives in a definer RPC or trigger.
2. Derive, don't copy: ownership-like state is computed from awards (as banners already are, `20261021000001:4-6`).
3. Pull-based bot contract: the bot reads a queue and writes back facts, success or failure; the site never calls Discord.
4. Smallest diff to existing RPCs: add setters/columns, don't rewrite upserts, `player_card` or the auth callback.
5. No dependency unless the browser can't do it.

**Decision drivers**
1. Correctness and safety under races, retries and privilege boundaries.
2. Fit with the existing pattern and tests (staff_can, allowlist test, queue shape).
3. Implementation and review cost for one plan across five components.

**Options**

*D1. Discord role queue*
- **(Chosen) Derived state + status ledger (applied | failed, retry_after).**
  Pros: self-heals on races, role edits, drafts, bans, deletes, unlinks; retries
  without a poison loop; no edits to award RPCs. Cons: join per poll; a ledger
  with outbox-like status columns.
- **Outbox table filled by triggers.** Pros: cheap reads, history. Cons: one
  trigger per change source; a lost or reordered item leaves Discord wrong for good.

*D1b. Who may map a role*
- **(Chosen) Admin-curated allowlist, community staff pick.** Pros: closes the
  self-award escalation; keeps mapping on the achievement form. Cons: one more
  table and a settings list.
- **Mapping admin-only.** Pros: no table. Cons: event staff, who make most
  badges, need an admin for every role-bearing badge.

*D2. Check-in token*
- **(Chosen) HMAC over 30 s windows, per-event secret, rotatable; 5-min proof for sign-in.**
  Pros: no write per rotation; one verify function; rotation revokes all. Cons:
  pgcrypto dependency (pre-checked); proof lengthens the relay window to 5 min.
- **Stored rotating row.** Pros: per-token revocation. Cons: a write every
  30 s per open screen, cleanup, multi-screen races.

*D3. Notifications*
- **(Chosen) DB triggers (statement-level for inserts) + cron for reminders.**
  Pros: every path notifies, including `lift_ban`; set-based; pgTAP-testable.
  Cons: logic out of sight of TS readers.
- **App-layer inserts.** Cons: misses non-action paths; needs a service-role insert RPC.

*D4. Reminder → bell*
- **(Chosen, rev 2) pg_cron `event_reminders_notify` with `notified_at`.**
  Pros: bell works when the bot is down; consistent with principle 1;
  testable by calling the function. Cons: bell and Discord can differ by ≤ 5 min.
- **Trigger on the bot's `sent_at` write-back.** Pros: one timestamp. Cons: no
  bot, no bell; rejected.

## ADR (draft)

- **Decision:** Ship Phase 5 as five migrations (`20261026000001` …
  `20261029000001`) with:
  - an admin-curated Discord role allowlist;
  - a derived-state role queue with an applied/failed ledger and retry backoff;
  - HMAC-window check-in tokens with a rotatable per-event secret and a 5-min sign-in proof cookie;
  - attendance-based event history with a backfill;
  - "latest due only" reminders, with the bell driven by pg_cron;
  - notifications from statement-level insert triggers and row-level status triggers;
  - `qrcode@1.5.4` (server-only) as the only new runtime dependency.
- **Drivers:** correctness/safety under races, retries and privilege
  boundaries; fit with the definer-RPC + pull-queue pattern; bounded cost.
- **Alternatives considered:**
  - outbox role queue;
  - admin-only role mapping;
  - stored rotating token rows;
  - a `next` query parameter through the OAuth callback (rejected, see `route.ts:20-22`);
  - app-layer notification inserts;
  - a reminder bell driven by the bot write-back;
  - auto-award on check-in (dropped in the interview);
  - Realtime bell (a non-goal);
  - a scanner library;
  - a hand-written QR encoder.
- **Why chosen:** each choice removes a class of drift or abuse (role
  escalation, stuck role items, token rows, lost check-ins across sign-in,
  missed notification paths, reminder spam) without touching existing award,
  upsert, player-card or callback code.
- **Consequences:**
  - Queue reads are joins.
  - The bot must write back successes and failures, and must run as a single instance.
  - Admins curate the assignable role list.
  - The camera opens only on the staff check-in route.
  - `/welcome` gains a cookie-based redirect.
  - `eventHistory()` is removed, with history backfilled from awards.
  - Retroactive banner unlocks via `admin_set_event_banner` don't notify.
- **Follow-ups:**
  - guild-join role resync RPC;
  - a lease for multi-instance bots;
  - a "new personal code" button;
  - notifications for retroactive banner unlocks;
  - per-token revocation if relayed check-ins become a problem.
