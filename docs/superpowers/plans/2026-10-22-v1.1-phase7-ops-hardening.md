**Spec:** `.omc/specs/deep-interview-v1.1-phase7-hardening-ops.md` (deep interview, 18% ambiguity) and

**Goal:** `/admin/server` grows into `/admin/ops`, where owner/admin monitor and manage every service (Minecraft,
Discord bot, whitelist-sync, the website, and future ones) through the server-manager, and edit the Discord bot's settings and see its automatic jobs. Website errors are
captured in-house. Every page meets a measured perf bar and an automated a11y/SEO bar.

**Architecture:** this repo ships the UI, a written manager API contract, mocks of that contract in
`scripts/local-mocks.mjs`, website error capture and a health endpoint the bot's status monitor probes. The
chulacraft-server-manager repo implements the contract (a Docker backend beside its systemd one, metrics, backups,
image updates) **separately**. The chulacraft-discord repo implements the bot side (settings from the database, job
reports, health check). Both follow contract docs written here. The website never touches Docker or hosts. Auth stays the same: 60 s EdDSA JWT per action, minted
after a role-check + audit RPC.

**Tech stack:** Next 16 App Router, React 19, Supabase (pgTAP), Vitest, Playwright. One new **dev** dependency:
`@axe-core/playwright`. No new runtime dependency.

## Global Constraints

- Ops is owner/admin only (`requireArea("admin")`). **Image pull & restart is owner-only** (RPC raises `FORBIDDEN`
  for admin). The admin token mask stays as today (`src/lib/mcsv-token.ts:24`: status, logs, console read,
  restart) plus the new backup bits. Start/stop/console write stay owner-only. Every mutating action writes an
  audit row with the token `jti`.
- Services come from the manager's config. The website renders whatever `/services` returns and has no service list
  of its own except the built-in `website` entry.
- **Restore is not a button.** It is a manual runbook step.
- `app_errors` stores message, digest, route (path only) and time. **No cookies, tokens, emails, query strings or
  user ids.** 30-day retention.
- Perf bar: admin page **server response p75 < 800 ms**; public pages **LCP < 2.5 s on mobile**. Fix only the pages
  that miss.
- Audit bar: axe zero serious/critical (375 px + desktop, light + dark); Lighthouse mobile Accessibility, SEO and
  Best Practices ≥ 95 on home, `/events`, `/events/[id]` and `/player/[id]`.
- Data pattern, grants allowlist and docs rule as in `docs/README.md`. Read
  `node_modules/next/dist/docs/` before using `instrumentation`, `after`, caching (`cacheTag`/`updateTag`), or
  metadata files.
- UI baseline: Thai font, loading/empty/error states, 375 px, keyboard, reduced motion. Status is always shown as
  text plus an icon, never colour alone.
- No commit without kaikub's approval. `graphify update .` after code changes.

## Review Focus

1. **Manager down or slow:** `/services` times out (5 s) or one service's status returns 500. The page still renders,
   the website entry still shows, and only the affected panel shows an error. Tested in Task 4 against the mock
   `fail` service.
2. **Error flood:** a render loop throws 1000×. The client sends at most 5 reports per fingerprint per page load, the
   endpoint caps at 60 per minute per IP-hash, and the reporter's own failure never throws. Tested in Task 1.
3. **Secrets in error text:** a message containing a JWT, `sb_secret_…`, an email, or `?code=` in a URL is stored
   redacted. Tested in Task 1 (`scrub`).
4. **Unexpected manager data:** ids with `/` or `..`, an unknown `state`, missing fields, or 500 services. Bad ids
   are dropped, an unknown state renders as "Unknown", and the list is capped at 50. Tested in Task 3 (`parseServices`).
5. **Stale public page after an admin save** (the Phase 4 bug). With caching on, a settings save is visible on the
   very next public load. Tested in Task 8.

## Decisions

- **What actually runs (checked in the sibling repos, 2026-10-22):** on one host, Minecraft runs as systemd
  `minecraft@<instance>.service`, and the whitelist worker and Discord bot run as **Docker** containers. The
  manager (Rust, axum) knows only systemd. It talks to D-Bus, reads logs from the journal, and lists only
  `minecraft@*.service` (`chulacraft-server-manager/src/mcsv_mgr.rs:224`). Its API docs live in
  `chulacraft-docs/docs/mcsv/api/`.
- **Two backends in the manager.** `systemd` (existing) and `docker` (new). The manager config lists each service:
  id, name, backend, and the unit or container name. For Docker it also lists the compose file and service used for
  updates. Docker access goes through a **filtering socket proxy** that only allows container list/inspect/logs/stats/
  start/stop/restart and image inspect/pull, because raw `/var/run/docker.sock` is root-equivalent. Compose updates run
  `docker compose -f <file> pull <svc> && docker compose -f <file> up -d <svc>`. Metrics come from cgroup properties
  over D-Bus (`CPUUsageNSec`, `MemoryCurrent`) for systemd and from `/containers/<id>/stats?stream=false` for Docker.
  The manager keeps 7 days of 5-min samples; how it stores them is its own choice.
- **Contract first.** `docs/ops-manager-contract.md` is the single source of truth for both repos. When it is
  final, it is also copied into `chulacraft-docs/docs/mcsv/api/` next to the existing endpoint docs.
  `src/lib/ops.ts` types mirror it, and the mocks implement it.
- **Endpoints** (all JWT-authenticated, JSON, and checked against the permission bit shown):
  - `GET /services` (STATUS) → `[{ id, name, kind: "systemd"|"docker", console: boolean, actions: ("start"|"stop"|"restart")[], backups: boolean, updatable: boolean }]`
  - `GET /service/:id/status` (STATUS) → `{ state: "up"|"down"|"restarting"|"unknown", since, last_restart, cpu_pct, mem_bytes, mem_limit_bytes }`
  - `GET /service/:id/metrics?hours=24` (STATUS) → `[{ t, cpu_pct, mem_bytes }]` at 5-min points
  - `GET /service/:id/uptime?days=7` (STATUS) → `[{ t, up_ratio }]` hourly
  - `GET /service/:id/rlog` (LOGS) and the console WebSocket (CONSOLE_READ/WRITE): the existing endpoints,
    generalised from `/server/:id`. The manager keeps `/servers` and `/server/:id/*` as aliases until the website
    has switched over.
  - `POST /service/:id/{start|stop|restart}` (START/STOP/RESTART)
  - `GET /backups` (BACKUP_READ) → `[{ id, target, kind: "manual"|"nightly", size_bytes, created_at, status: "running"|"ok"|"failed" }]`.
    `POST /backups { target }` (BACKUP_RUN) → `202 { id }`. Targets are the Minecraft world and the Supabase dump.
    Retention (last N) and the nightly time are manager config.
  - `GET /service/:id/image` (STATUS) → `{ current, latest, checked_at }`. `POST /service/:id/update` (UPDATE) =
    pull + recreate.
- **New permission bits** in `PERMISSION`: `BACKUP_READ: 128`, `BACKUP_RUN: 256`, `UPDATE: 512`. Admin mask gains
  `BACKUP_READ | BACKUP_RUN`. Owner keeps `ALL`.
- **Alerts stay in the bot's status monitor** (kaikub's choice). It already posts 🔴 after two failures and 🟢 on
  recovery for Minecraft, the website, Supabase and the whitelist queue (`chulacraft-discord/src/status-monitor.js`).
  The bot repo adds one check: `GET /api/ops/health`, which is down when the endpoint fails or `ok` is false, and
  sends an **error spike** alert when `errors_5m ≥ 10`. The manager sends no alerts. Known gap, already in the bot
  README: nothing alerts when the bot's own host is down. The Ops page still shows the bot container as down.
- **Website as a service.** `GET /api/ops/health` with `Authorization: Bearer <OPS_HEALTH_TOKEN>` (new server-only
  env, compared in constant time) returns `{ ok, db: "ok"|"down", errors_5m, version }`. `version` = `VERCEL_GIT_COMMIT_SHA` short. The bot's status
  monitor probes it every 60 s, which gives the website uptime and the error-spike alert. In `/admin/ops` the website row reads its own health directly, not through the manager.
- **Error capture:** `src/instrumentation.ts` `onRequestError` and `src/app/api/client-errors/route.ts` (POST,
  same-origin only, body ≤ 2 KB) both call `recordAppError` → `record_app_error` (service_role only). Client
  reporting is a small `reportError()` called from `src/app/error.tsx`, `src/app/admin/error.tsx` and a new
  `src/app/global-error.tsx`. The CSP (`src/proxy.ts`) already allows same-origin `connect-src`.
- **Access RPC:** `admin_ops_access(p_jti uuid, p_service text, p_action text) returns text` replaces
  `admin_server_console_access`, which is dropped in the same migration once `manager.ts` calls the new one. Actions:
  `status, logs, console, console_write, start, stop, restart, backup_list, backup_run, update`. `update` requires
  `owner`. Every action that isn't a read is logged with entity `ops` (old rows keep `server_console`).
- **Routes:** `/admin/ops` (list + backups section), `/admin/ops/[service]` (detail), `/admin/ops/website` (error
  feed + health). `next.config.ts` redirects `/admin/server` → `/admin/ops` (permanent). Nav: "Server" → "Ops"
  (`src/app/admin/admin-nav.tsx:10`).
- **Caching (only if Task 7 shows public pages missing the bar):** `'use cache'` + `cacheTag` on the
  `src/lib/site-content.ts` reads, and `updateTag` (read-your-own-writes in server actions, see
  `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/updateTag.md`) in every content save action.
  This targets the Phase 4 stale-once bug, which came from `revalidateTag`'s stale-while-revalidate.

### 5. Discord bot settings + automatic tasks (`/admin/ops/bot`)

Added after the interview, at kaikub's request: admins change the bot's channel/role IDs from the site and see
every automatic job the bot runs. Pull-based through the database, like `docs/bot-contract-phase5.md`. The bot
repo implements it separately.

**Where the settings live (kaikub: "save the config in db").** Editable values are stored in Supabase
(`bot_settings.value`). The bot's `.env` keeps the **secrets** (`DISCORD_TOKEN`, `OPENROUTER_API_KEY`,

default**, so the bot still starts with the database down. Effective value = database value if set, otherwise the
`.env` value. `db.json` (join-to-create lobbies, managed messages, the bot-owned `academicRoles` map) stays on the host
in v1. Moving managed messages and lobbies into the database is a possible follow-up.

    | Kind | Rule |
    |---|---|

  (`ROLE_MANAGED_BY_BOT`). The database can now enforce the bot-managed-roles rule the Phase 5 contract left to the bot.
- **No secrets:** the contract forbids registering the token or any secret. `bot_register` refuses a key matching
  `token|secret|password|key$` (`INVALID`), so a mistake in the bot can't put the token on a web page.
- Overdue means an enabled, non-retired job with a non-null interval whose `last_started_at` is older than
  3 × `interval_seconds`. The bot is the alerter, so it can't alert about itself. The Ops page shows overdue jobs,
  and the bot container's Docker status shows it is down.
- **Bot-side health check:** the contract also tells the bot's status monitor to probe `/api/ops/health` (Task 1)
  and alert on an error spike (see Decisions → Alerts).
